# DSA docs and website redesign interview

## Goal

Restructure the DSA website so the roadmap and practice companion are split into stage-specific, easy-to-navigate content while simplifying the UI and applying the requested visual and behavior fixes.

## Status

Interview complete. Shared understanding confirmed. Ready for implementation when requested.

## Facts found

- The Astro site has 19 stages in `src/data/stages.ts`, stage pages in `src/pages/stage/[slug].astro`, and full-document pages in `src/pages/roadmap.astro` and `src/pages/practice.astro`.
- The two source Markdown documents are very large: roadmap 4,250 lines and practice companion 6,214 lines.
- Current stage pages show generic five-pass content, a generic practice callout, two stage resource links, and a `KEEP THE RULE VISIBLE` note; they do not yet render stage-specific sections from both source documents.
- Current reference pages render each full Markdown file as one long article. The roadmap has a stage index, but the practice page does not have a comparable stage index.
- `Ask AI`, `Download`, and `Share` are implemented as native `<details>` menus in `src/components/AskTools.astro`.
- Theme support exists in `BaseLayout.astro` and `src/scripts/site.ts`, with dark-theme CSS in `src/styles/global.css` and an older static implementation in root `app.js`/`styles.css`.
- The current footer includes `Open source. No backend. Your progress stays local.` and the header contains a dark-theme toggle.
- The repository currently has no reported working-tree changes at inspection time.
- The requested website URL is `https://rudra-g-23.github.io/dsa-for-data-science`.

## Settled decisions

- Q1: Each stage page combines the relevant roadmap content and practice-companion content.
- Q2: Navigation uses a library-style sidebar with all 19 stages and nested stage subsections.
- Q3: Move the two large source Markdown files to `resources/` and update imports/links.
- Q4: Keep full roadmap and practice pages, each with a working table of contents and stage anchors.
- Q5: Provide previews for both internal and external links.
- Q6: Keep Ask AI, Download, and Share in a sticky viewport-safe toolbar; close menus on scroll, outside click, Escape, and after actions.
- Q7: Use a white/light visual system with `#5e17eb` as a restrained accent.
- Q8: Replace the boxed `{ }` mark with a simple custom SVG data-structure/connected-node logo.
- Q9: Add and display a real `Last updated` date for each source document and its rendered pages.
- Q10: Remove the generic five-pass block, `KEEP THE RULE VISIBLE`, generic data-workload prompt, and repetitive promotional copy; retain meaningful source content.
- Q11: Remove the unused legacy root `index.html`, `styles.css`, and `app.js` after confirming Astro does not depend on them.
- Q12: Redesign dark artwork/social previews for the light system and make the homepage preview show the actual stage/library experience.
- Q13: Use icons throughout the cleaned interface where they improve recognition and navigation.
- Q14: Keep and improve the existing Skills page as part of the redesigned site.
- Q15: Use a consistent inline SVG icon set for navigation and actions instead of text-symbol UI controls.
- Q16: Make Skills a top-level navigation item with its own index/sidebar, without duplicating every skill under every stage.
- Q17: Render real local `SKILL.md` content on the Skills page and retain GitHub links for source browsing.
- Q18: Make the homepage preview a functional miniature of the library/stage interface.
- Q19: Include only clearly stage-owned source sections on each stage page; keep global templates, schedules, directories, and completion guidance on dedicated reference pages.
- Q20: Preserve existing public URLs for stage and reference pages.
- Q21: Preserve useful Markdown content and filenames; remove only explicitly rejected filler and update metadata.
- Q22: Completion requires production build, link/path checks, Markdown/TOC validation, desktop/mobile visual inspection, and removal of dark-theme code.
- Q23: Generate stage content and tables of contents at build time; use client-side code only for interaction.
- Q24: Do not create a commit unless explicitly requested.
